# Hosted pipeline audit — 2026-10-21

## Findings and changes

The hosted-only refactor still contained application-specific language rules:

- Claim search expanded hand-written synonyms and interpreted status words.
- Follow-up retrieval recognized a fixed list of phrases.
- Claim extraction allowed only two sample-policy categories; the review form also offered those categories as presets.
- Chunking expected the sample policy's numbered heading format.
- The policy prompt defined conditional coverage in terms of appraisal/value thresholds instead of arbitrary policy prerequisites.

Those production rules have been removed. Policy retrieval uses hosted semantic embeddings plus generic BM25 rank fusion. A hosted model rewrites conversational references, extracts unrestricted claim categories, and evaluates retrieved policy evidence against general verdict definitions. Claim search filters ownership before embedding records, ranks semantic candidates, then uses a validated model selection to apply the requested meaning and status. No synonym dictionary or local inference fallback is used.

Markdown hierarchy and plain text are accepted; long sections have bounded overlapping chunks. Collections include the embedding endpoint/model and corpus fingerprint in their identity. A changed policy is indexed before replacing the active corpus and lexical snapshot. Exact source IDs and evidence quotes are verified. These checks establish provenance, not correctness of interpretation.

Embedding responses are batched and checked for missing/duplicate indexes, finite nonzero vectors, and consistent dimensions. The live Gemini endpoint omitted one response index; the adapter now recovers it only when exactly one index can be uniquely inferred. Ambiguous ordering fails instead of silently attaching vectors to the wrong documents.

## Evaluation integrity

The original 25 questions and expected verdicts were left unchanged. The scorer previously awarded citation credit to an incorrect unsupported answer; it now requires evidence for expected supported answers. Additional valid supporting sections are allowed, but the required expected sections must be present. Errors count against the run, and invalid semantic outputs are not retried until they pass. SDK transport retries remain enabled.

Unit tests use explicit test-only fakes, some with sample-policy fixtures. They verify orchestration and contracts, not language understanding. No production module imports them. Hosted evaluations use the real configured language model and embeddings, isolated temporary indexes, and fictional policies/claims only.

A separate eight-question policy covers rented equipment, EUR limits, reporting deadlines, permits, and exclusions. It checks whether the implementation transfers beyond the two original policy sections. A three-query hosted claim-search smoke test covers a paraphrase, a status filter, and no match.

## Remaining limits

- Verdict labels are generated by a model and can disagree with the expected rubric. Passing a small evaluation is not proof of universal reliability.
- Retrieval checks use small corpora. Multi-document scale, adversarial policies, and exhaustive numeric-answer accuracy are not established by these tests.
- Claim search examines at most 20 semantic candidates; broad lists are not guaranteed exhaustive. Embedding caches are in memory.
- Claim submission still uses the existing application's schema and explicit confirmation flow. This audit does not turn filing into verified coverage approval; the coverage check is model guidance, not a policy authorization boundary.
- Browser sessions are prototype identities, not verified policyholder accounts. Voice providers were not retested.
- UI labels, action names, identifier formats, field validation, ownership rules and public fixture IDs remain deterministic intentionally. They are application contracts, not policy knowledge or synonym rules.

## Follow-up fix: iterative retrieval and claim workflow

Every query now gets model preparation, including the first message. The original
message remains an independent search and is passed unchanged to policy analysis.
The model can request additional evidence with up to two focused queries per
round; the controller permits at most three rounds, deduplicates queries/sources,
and stops without accepting a provisional favorable answer when evidence remains
insufficient. Missing user facts lead to clarification rather than endless search.

The claim workflow checks the original message regardless of extracted fields.
The existing draft supplies context but never replaces the original facts. Edited
incidents are checked again before persistence; confirmation still requires an
explicit action and model text cannot authorize a write.

The hosted evaluator now uses this same iterative retrieval controller. Earlier
25/8-case scores above describe the earlier implementation, not a rerun of this
change. Targeted full-workflow live results are in
[claim_workflow_live.json](../backend/eval/claim_workflow_live.json).

Targeted hosted workflow results: 4/4 passed. The exact prolonged-sink-leak
message and a paraphrase return the documented exclusion; a sudden burst
proceeds to a draft; an unknown water source asks for clarification. Offline
regressions also cover evidence expansion, exhausted/repeated search budgets,
missing extracted fields, empty initial retrieval, and edited-confirmation checks.
Run `backend/.venv/bin/python backend/eval/eval_claim_workflow.py` from the project
root to repeat the opt-in live checks (uses the existing Gemini configuration).

## Coverage presentation follow-up

The previously unused response composer is now shared by policy answers and claim
coverage checks. It explains the fixed finding in a calm, respectful voice,
acknowledges reported damage, and avoids repeated verdict headings, invented
next steps, payment promises and boilerplate disclaimers. The original citations
and structured verdict remain unchanged. Unsupported numeric details are rejected;
a failed writing call falls back to the verified evidence. This adds a hosted
writing call; the prose remains model-generated and its correctness is not
guaranteed by the numeric guard.

All 96 backend tests pass. The user's floor-damage example was verified through
the full hosted workflow with the new writing step; see
[presentation_live.json](../backend/eval/presentation_live.json).

## Customer-service dialogue follow-up

Unresolved incident facts now produce one short question using the clarification
card, without policy recitals, limits or repeated verdict badges. Verified policy
passages are reused across replies after matching them against the active corpus.
Missing document evidence can still trigger the bounded retrieval loop.

Clarification state is persisted with the response. At most two questions are
allowed in an unresolved sequence; an identical question or an explicit inability
to supply the detail ends with a review notice. An explicitly different incident
can reset the sequence, based on the model's assessment. The original message and
history remain the source of incident facts; timing alone is not a coded proxy
for a covered cause.

When the user has requested compensation/filing and supplies enough information,
the same assessment leads to a short cited explanation and an editable claim
form. General policy questions do not automatically open a form. Persistence
still requires explicit confirmation.

Validation: 101 backend tests, 27 frontend tests and production build passed.
The user's four-turn conversation was replayed live with Gemini: two short
questions, then a cited claim form on the contextual reply “yeah sudden”; the
explicit pipe-break confirmation also kept the form. Results are saved in
[service_dialogue_live.json](../backend/eval/service_dialogue_live.json).
This is a targeted conversation check, not a new broad accuracy score.

## Explicit evidence review and final clarification writing

Before a customer clarification is allowed, a separate structured model review
checks relevant coverage grants, exclusions, conditions and cross-references.
When document evidence is insufficient, its focused queries feed the existing
three-round retrieval controller. Unresolved gaps stop with a review notice,
not a request for the customer to fill a document gap.

Clarification now has a dedicated final LLM writing step, with the original user
message, history, unresolved fact and reviewed policy passages. Its voice asks
about relevant contrasting possibilities neutrally, acknowledges reported damage,
and permits uncertainty instead of leading toward the covered cause. The existing
two-question ceiling remains in place. Provider failures use a neutral fallback.

All 104 backend tests passed; targeted controller tests also passed after tightening
the review condition. The real Gemini sink-example trace records evidence review
before clarification composition, with a warm question offering sudden damage,
gradual damage or uncertainty. See
[clarification_voice_live.json](../backend/eval/clarification_voice_live.json).
Model review reduces unsupported assumptions; it is not a guarantee of semantic
correctness. No broad accuracy evaluation was rerun for this presentation change.

## Uncertain mixed accounts: informative conclusion

When clarification stops, the final answer now uses the LLM presentation step
with the verified evidence and an uncertain verdict, without appending another
question. It explains the relevant coverage terms, limits/deductibles, exclusions,
and why the user's account cannot establish a cause. Citations remain attached.
It does not invent an outcome or replace useful details with a generic review notice.

All 105 backend tests passed. The exact two-turn mixed-cause example was replayed
with Gemini: the final answer explained the $25,000 sudden-burst coverage, $500
deductible and gradual-leak/flood exclusion, identified the unresolved distinction,
and cited sec1. See [uncertain_details_live.json](../backend/eval/uncertain_details_live.json).
